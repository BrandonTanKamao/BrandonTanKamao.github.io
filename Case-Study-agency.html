Custom-object architecture

What happens when a member is a company, not a person?

Before

A membership belonged to a business, and a business could have two owners, a team and shared partner contacts. The CRM only knew people. Every fact lived twice and the two copies drifted.

Built

A company record for every membership, linked to its people. Ten sync workflows moving facts up (person to company) and down (company to people), fourteen more mirroring partner fields, and two webhook Zaps running one shared script that checks the source state before it writes anything.

The part that takes experience

Tags used as one-shot doorbells, removed once heard. One trigger per dropdown value to beat the slug-versus-label problem. Triggers kept asymmetric so a downward write can never create an upward event. The script refuses to write unless the source record really says what the request claims.

CRM migration and data rescue

How much of your history survives the move?

Before

Years of notes, contacts and sponsor history in a CRM with a renewal date. Spreadsheets stripping leading zeros off zip codes. An automation quietly writing one hard-coded value over real data.

Built

A scripted migration with staged modes (plan, go, verify, restore) so every write could be previewed and rolled back. An account-wide audit that found what was wrong before anyone noticed. A reconciliation across three systems.

The part that takes experience

Every repair script writes a ledger first and refuses to run twice. Findings are tagged by how they were established (measured, documented, inferred) so a guess never gets quoted as a fact. A retractions file keeps every wrong call so it is never repeated.

Debugging

Can you debug the platform itself, or only the workflows on it?

Found a HighLevel bug and got it fixed

An RSS email campaign was rendering a block tag wrong on every send. I isolated it, wrote the reproduction with the raw feed and the rendered output, filed it, and when HighLevel shipped the fix I proved it on the next live send before telling the client it was done.

Support said one thing, the API said another

Support called a wrong SMS sender stamp a display quirk. I pulled the stored message records: three contacts with one owner showed five different senders across 82 messages. The stamp follows the sending number, and I had the data to show it.

714 skipped emails, one real cause

Support said the skips were already-sent contacts. That explained 152 of 714. The platform's own skipped export showed 351 unmailable contacts as the real cause.

"Our emails are going to spam"

They were not. Same domain, same sender, both months. The statistics dashboard showed 0.78% bounce and 0.018% complaints. The only change was list size. The fix was list hygiene, not a new domain.
